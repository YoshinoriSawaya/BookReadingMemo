# Book Reading API

本プロジェクトは、書籍の読書記録、引用（Quote）、思考・メモ（Thought）を管理するための Web API です。

## アーキテクチャの概要

本 API は、機能ごとの凝集度を高め、保守性と拡張性を向上させるために **フィーチャーベース（垂直スライス）アーキテクチャ** を採用しています。
従来のレイヤーごとのディレクトリ分割（Controllers, Services, Models...）を廃止し、ドメイン機能（Feature）ごとに必要な要素をカプセル化しています。

### 採用している設計原則
* **関心の分離 (Separation of Concerns):** ビジネスロジック、データアクセス、APIのエンドポイント定義を明確に分離。
* **依存性逆転の原則 (Dependency Inversion Principle):** `UseCase` や `Repository` はインターフェースに依存し、実装の詳細（データベースや外部API）から分離。
* **単一責任の原則 (Single Responsibility Principle):** 各機能が自身のドメイン知識のみを持つように設計。

## ディレクトリ構成と役割

プロジェクトの主要なディレクトリ構造とその役割は以下の通りです。

### 1. `Features/` (中核機能)
アプリケーションの各機能（ドメイン）ごとにフォルダを分割しています。新しい機能を追加する場合は、この配下に新しいフォルダを作成し、その中で実装を完結させます。

現在存在するフィーチャー:
* `Book/` : 書籍情報および外部書籍API連携に関する機能
* `Quote/` : 書籍からの引用に関する機能
* `Thought/` : 読書を通じた思考・メモ・タグ付けに関する機能
* `User/` : ユーザー情報に関する機能

**各機能（Feature）内の標準的な構造:**
* `Controllers/` : HTTPリクエストを受け取り、レスポンスを返すAPIエンドポイント。ロジックは持たず、`UseCase` を呼び出します。
* `UseCase/` : アプリケーションのビジネスロジック（ユースケース）をカプセル化する層。
* `Repositories/` : データベース（EF Core）や外部APIへのアクセスを抽象化する層。必ずインターフェース（`I...Repository`）を定義し、DI コンテナに登録します。
* `Entities/` : データベースのテーブルとマッピングされるドメインモデル。
* `DTOs/` : クライアントとのデータのやり取り（リクエスト/レスポンス）専用のデータ転送オブジェクト。APIの契約（Contract）を定義します。

### 2. `Core/` (共通基盤)
アプリケーション全体で共有される要素を配置します。
* `Entities/` : 共通の基底エンティティ（`BaseEntity.cs` など）。
* `Constants/`, `Enums/` : システム全体で利用する定数や列挙型。
* `Exceptions/` : カスタム例外クラス。

### 3. `Data/` (インフラストラクチャ)
データベース接続などのインフラ層に関する設定を配置します。
* `AppDbContext.cs` : Entity Framework Core のコンテキストクラス。

## 開発ガイドライン：新機能の追加手順

新しいAPIエンドポイントを追加する際の基本的なデータフローは以下のようになります。

1.  **DTOの定義:** `Features/{FeatureName}/DTOs/` にリクエストとレスポンスの型を定義します。
2.  **Entityの定義:** データベースに保存するデータ構造が必要な場合は `Entities/` に定義し、`AppDbContext` に追加して Migration を実行します。
3.  **Repositoryの実装:** データの保存・取得ロジックを `Repositories/` にインターフェースと共に実装します。
4.  **UseCaseの実装:** `UseCase/` にビジネスロジックを実装し、Repository のインターフェースを利用（DI）してデータを処理します。
5.  **Controllerの追加:** `Controllers/` でエンドポイントを公開し、作成した UseCase を呼び出して DTO を返却します。

## 設計思想：クリーンアーキテクチャとプラグマティックなアプローチ

本プロジェクトでは、クリーンアーキテクチャやドメイン駆動設計（DDD）のエッセンスを取り入れつつも、過度な複雑さを避けるために「あえて厳密にしていない」部分を設けています。

### 🛡️ 厳密に適用している部分（守るべきルールの境界線）

保守性とテスト容易性を担保するため、以下の原則は厳密に適用しています。

* **依存性逆転の原則 (DIP) の徹底**
  `UseCase` はデータベースや外部APIの具体的な実装を直接呼び出しません。必ず `Repositories/` に定義されたインターフェース（`I...Repository`）に依存し、DI（依存性の注入）経由で実行します。これにより、ビジネスロジックの単体テスト（モック化）が容易になっています。
* **モデルとコントラクト（契約）の分離**
  データベースの構造を表す `Entity` と、APIの入出力を表す `DTO` は明確に分けています。DBスキーマの変更がAPIのレスポンスに意図せず影響を与えることを防ぎ、APIバージョニングや仕様変更に強い設計としています。
* **ビジネスロジックのカプセル化**
  Controller にはリクエストの受け取りとレスポンスの返却（および必要に応じたバリデーション）のみを記述し、実際の機能の振る舞いはすべて `UseCase` に閉じ込めています（ファットコントローラーの禁止）。

### ⚖️ あえて厳密にしていない部分（実用性・DXを優先した妥協点）

開発スピード（DX）と認知負荷の軽減を優先し、厳密なクリーンアーキテクチャから以下の点を意図的に崩しています。

* **レイヤー間の物理的な完全分離（プロジェクト分割）の省略**
  厳密なクリーンアーキテクチャでは、Domain、Application、Infrastructure などを別々のクラスライブラリ（プロジェクト）に物理的に分割し、コンパイルレベルで依存を強制します。しかし本APIでは、機能ごとの凝集度を高める **垂直スライス（フィーチャーベース）** を優先し、同一フォルダ（`Features/{FeatureName}/`）内にインターフェースも実装（インフラストラクチャ）も同居させています。
* **データモデル（Entity）とドメインモデルの共用**
  厳密なDDDでは、インフラ層のORM（EF Core）が要求するデータモデルと、純粋なビジネスルールを持つドメインモデルを別に定義し、マッピング層を挟みます。本APIでは冗長なマッピングを避けるため、EF Coreの `Entity` クラスをそのままドメインモデルとして扱っています。
* **CQRSの未導入（シンプルなCRUD構成）**
  現在の要件において読み取りと書き込みのモデルを完全に分離するほどの複雑性はないと判断し、一つの Repository と UseCase でデータの参照と更新の両方を扱っています。将来的に特定の参照系のパフォーマンス要件が厳しくなった場合にのみ、部分的な導入を検討します。
